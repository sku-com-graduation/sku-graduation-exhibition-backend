# 업로드 구조 개선, 무엇을 얼마나 쟀나

전시 작품의 이미지와 영상 업로드를 **서버 중계**에서 **Pre-signed URL + S3 Multipart**로 바꿨다.
이 문서는 그 개선을 숫자로 확인한 기록이다.

## 1. 두 구조의 차이

**이전, 서버 중계** (git `0f92987` 이전, `S3Uploader.uploadToS3`)

```
프론트 ──파일 전체──▶ 백엔드 ──파일 전체──▶ S3
```

백엔드가 `MultipartFile`로 파일을 받는다는 건 **서블릿 컨테이너가 파일을 끝까지 다 받아
디스크에 떨궈 둔 뒤에야 컨트롤러가 호출된다**는 뜻이다. 그래서 두 구간이 겹치지 않고
차례로 흐른다. 업로드 완료 시간 ≈ (프론트→백엔드) + (백엔드→S3).

**현재, Pre-signed URL**

```
프론트 ──URL 요청──▶ 백엔드 (URL만 발급, 파일은 지나가지 않음)
프론트 ──파일 전체──▶ S3
```

영상은 여기에 S3 Multipart Upload를 얹어 청크로 나눠 병렬 전송하고, 실패한 청크만 다시 보낸다.

## 2. 이미 측정한 것, 백엔드가 지는 부담

`ExhibitionListQueryCountTest` 옆의 [`UploadPathCostTest`](../../src/test/java/com/ghostHoliday/graduationExhibitions/performance/UploadPathCostTest.java)가
두 구조를 나란히 돌려 잰다. 예전 코드는 테스트 안에 그대로 재현해 뒀다.

```bash
./gradlew test --tests "*UploadPathCostTest"
```

**100MB 파일 1건 기준**

| 항목 | 서버 중계(이전) | Pre-signed(현재) |
|---|---|---|
| S3 로 다시 보내던 구간 | 75 ms | 없음 |
| 요청 스레드 점유 시간 | 421 ms | 1 ms |
| 백엔드를 통과한 바이트 | 200 MB | 48 B |
| 백엔드 임시 파일 최대 | 100 MB | 0 |
| S3에 도착한 바이트 | 100 MB | 100 MB |

10MB 기준으로는 25ms / 115ms / 20MB / 10MB 가 없음 / 2ms / 49B / 0 으로 바뀐다.

바이트와 임시 파일은 결정적인 값이다. 시간 두 줄은 반복 실행 중앙값이고 머신에 따라 달라진다.

### S3 로 다시 보내던 구간이 곧 업로드에 얹히던 시간이다

`MultipartFile`로 파일을 받는다는 건 **서블릿 컨테이너가 파일을 끝까지 다 받아 디스크에 떨궈
둔 뒤에야 컨트롤러가 호출된다**는 뜻이다. 그래서 컨트롤러가 S3로 다시 보내는 구간은 사용자
전송과 겹치지 않고 **그 뒤에 따로 흐른다.** 사용자가 기다리는 시간에 그대로 더해진다.

테스트는 그 구간만 따로 잰다. 100MB 기준 75ms 인데, 이 값은 S3 자리에 **로컬 스텁**을 뒀을
때의 값이다. 루프백은 사실상 무한대 대역이라 여기서는 거의 0에 가깝게 나온다. 실제 EC2에서
S3로 보낼 때는 100MB를 그 구간의 대역폭으로 나눈 만큼 걸린다. 즉 **75ms 는 하한**이고, 진짜
값은 5절대로 재야 한다.

없어진 건 이 구간이다. 업로드 지연 문제를 고친 게 맞고, 다만 그 크기를 로컬에서는 하한까지만
보일 수 있다.

## 3. 업로드가 몰릴 때 옆 사람이 겪는 시간

2절은 업로드 1건의 비용이다. 그 비용이 쌓이면 무슨 일이 생기는지는
[`UploadConcurrencyCostTest`](../../src/test/java/com/ghostHoliday/graduationExhibitions/performance/UploadConcurrencyCostTest.java)
가 잰다. 재는 대상은 업로드하는 사람이 아니라 **그 옆에서 목록을 보고 있는 사람**의 응답 시간이다.

```bash
./gradlew test --tests "*UploadConcurrencyCostTest"
```

`MultipartFile` 을 받는다는 건 파일이 다 도착할 때까지 톰캣 요청 스레드 하나가 묶여 있다는
뜻이다. 사용자의 회선이 느릴수록 오래 묶인다. 동시 업로드가 스레드 수를 넘기면 그 뒤에 온
평범한 조회 요청까지 큐에서 기다린다.

**측정 조건.** 톰캣 스레드 10개, 동시 업로드 16건, 파일 8MB, 업로드 쪽 상행 1MB/s.
조회 API 는 DB 를 타지 않는 가장 가벼운 요청이다.

| | p50 | p95 | 최대 |
|---|---|---|---|
| 업로드 없음 | 4.4 ms | 6.7 ms | 67.9 ms |
| 서버 중계(이전) | 7,879.8 ms | 7,885.6 ms | 7,891.2 ms |
| Pre-signed(현재) | 3.1 ms | 4.0 ms | 4.1 ms |

스레드 수를 10으로 줄인 건 포화 지점을 앞당기기 위해서다. 운영 기본값은 200 이므로 같은 일이
벌어지는 지점이 동시 업로드 200건으로 옮겨갈 뿐 구조는 같다.

## 4. 업로드 1건 총 소요 시간

같은 테스트가 업로드 1건의 완료 시간도 잰다. 상행 1MB/s 에서 8MB 파일 기준이다.

| 경로 | 완료까지 |
|---|---|
| 서버 중계(이전) | 8,021.2 ms |
| Pre-signed(현재) | 8,007.5 ms |
| 차이 | 13.8 ms |

차이가 13.8ms 뿐인 이유는 **여기서도 S3 자리가 로컬 스텁**이기 때문이다. 되보내기 구간이
공짜에 가까우니 그만큼만 줄어든다. 이 표는 "개선 효과가 없다"가 아니라 **"로컬에서는 되보내기
구간의 크기를 잴 수 없다"**는 뜻으로 읽어야 한다.

실제 배포에서는 되보내기 구간이 100MB를 EC2와 S3 사이 대역폭으로 나눈 만큼이고, 여기에
디스크에 100MB를 쓰고 다시 읽는 시간이 붙는다. 그만큼이 사용자가 기다리던 시간에서 빠진다.

멀티파트 병렬 전송은 여기에 하나를 더 얹는다. 커넥션 하나로는 긴 거리 회선의 대역을 다 쓰지
못하는데, 여러 커넥션으로 나눠 보내면 그 손실이 준다. 이것도 실제 S3가 있어야 관측된다.

## 5. 멀티파트 병렬은 얼마나 이득인가

Pre-signed URL 은 파일이 백엔드를 지나가지 않게 만든 개선이고, S3 멀티파트 병렬은 그 위에
올린 별개의 개선이다. 앞의 것은 2절과 3절이 뒷받침하는데 뒤의 것은 숫자가 없었다.
[`MultipartParallelUploadTest`](../../src/test/java/com/ghostHoliday/graduationExhibitions/performance/MultipartParallelUploadTest.java)
가 그걸 잰다.

### 루프백에서는 못 잰다

커넥션 하나의 처리량은 대략 혼잡 윈도우 나누기 RTT 다. 루프백은 RTT 가 0 에 가까워서
커넥션 하나로도 대역을 다 쓴다. 그 위에서 재면 파트를 8개로 나눠도 시간이 그대로 나오고,
"멀티파트는 효과 없음" 이라는 틀린 결론이 나온다. 4절에서 총 소요 시간이 거의 같게 나온
것과 같은 함정이다.

### 그래서 지연이 있는 링크를 만든다

S3 자리에 도커 컨테이너를 놓고 그 안에서 `tc netem` 으로 지연을 건다. 커널이 실제로 패킷을
늦추므로 TCP 혼잡 제어와 윈도우 증가가 진짜로 일어난다. 모델을 계산한 게 아니라 실제 TCP
동작을 잰 것이다. 절대값은 AWS 와 다르지만 병렬이 이기는 이유와 그 크기가 RTT 에 어떻게
걸리는지는 같다.

```bash
docker run -d --name s3sink --cap-add=NET_ADMIN -p 9000:9000 \
  -v "$PWD/src/test/resources/bench:/app" -w /app python:3.12-slim python sink.py
docker exec s3sink sh -c "apt-get update -qq && apt-get install -y -qq iproute2"
docker exec s3sink tc qdisc replace dev eth0 root netem delay 30ms

./gradlew test --tests "*MultipartParallelUploadTest" \
  -Dbench.sink=http://localhost:9000 -Dbench.rtt=30ms
```

### 결과

파트 10MB, 링크 지연 30ms, 3회 반복 중앙값.

| 파일 | 단일 PUT | 병렬 2 | 병렬 4 | 병렬 8 |
|---|---|---|---|---|
| 100 MB | 1.94 s | 1.05배 | 1.73배 | 2.58배 |
| 500 MB | 8.00 s | 0.80배 | 1.47배 | 2.31배 |
| 1 GB | 16.22 s | 0.79배 | 1.61배 | 2.51배 |

병렬 8 의 절대값은 각각 0.75초, 3.46초, 6.46초다.

같은 걸 지연 없이 돌린 대조군.

| 파일 | 단일 PUT | 병렬 2 | 병렬 4 | 병렬 8 |
|---|---|---|---|---|
| 100 MB | 0.11 s | 1.42배 | 1.84배 | 1.27배 |
| 500 MB | 0.45 s | 1.24배 | 1.35배 | 1.04배 |
| 1 GB | 0.81 s | 1.11배 | 1.19배 | 0.88배 |

**이득이 통째로 사라진다.** 1GB 는 오히려 0.88배로 느려진다. 병렬로 얻는 게 없는데
파트마다 커넥션을 새로 여는 비용은 그대로 들기 때문이다.

### 읽을 때

- **이득은 지연에 걸려 있다.** 대조군이 그걸 보여준다. 서울 리전에 유선으로 붙으면 RTT 가
  작아 이득이 줄고, 모바일이나 회선이 나쁜 환경일수록 커진다. 그래서 이 수치를 인용할 때는
  지연 조건을 반드시 같이 적는다.
- **병렬 2는 손해다.** 500MB 와 1GB 에서 0.80배, 0.79배다. 파트마다 커넥션을 새로 열어
  slow start 를 다시 겪는 비용이 병렬 이득보다 크다. 잘게 나눌수록 좋은 게 아니고,
  나눴으면 충분히 동시에 보내야 본전을 넘는다.
- **파일이 파트 크기 이하면 멀티파트는 아무 일도 안 한다.** 파트가 하나뿐이라 단일 PUT 과
  같다. 파트 10MB 로 잡으면 10MB 이하 파일에는 의미가 없다.

### 끊겼을 때 다시 보내야 하는 양

속도와 별개로 멀티파트가 주는 게 하나 더 있다. 같은 테스트의 두 번째 케이스가 잰다.
싱크가 지정한 바이트까지만 읽고 연결을 끊어 실제로 실패를 만들고, 클라이언트가 흘려보낸
바이트를 세서 비교한다.

1,000MB 파일, 파트 10MB, 99% 지점(마지막 파트를 절반쯤 보낸 시점)에서 끊었을 때.

| | 단일 PUT | 멀티파트 |
|---|---|---|
| 끊기기 전까지 보낸 양 | 996 MB | 997 MB |
| 다시 보낸 양 | 1,000 MB | 10 MB |
| 합계 | 1,996 MB | 1,007 MB |

단일 PUT 은 어디서 끊기든 처음부터다. 멀티파트는 끝난 파트가 이미 S3 에 올라가 있어
끊긴 파트만 다시 보낸다. **다시 보내는 양이 100배 차이난다.**

시간이 아니라 바이트라서 링크 지연과 무관하고, 머신도 타지 않는다. 그래서 이 표는
지연 조건을 붙이지 않고 그대로 인용해도 된다.

```bash
./gradlew test --tests "*MultipartParallelUploadTest.retransmissionCostOnFailure" \
  -Dbench.sink=http://localhost:9000
```

## 6. 아직 안 잰 것, 실제 S3

4절은 S3 자리에 로컬 스텁을 뒀다. 실제 리전까지의 거리, 커넥션당 처리량 한계, 멀티파트
병렬도의 효과는 진짜 S3 로 재야 한다. 재려면 아래대로 하면 된다.

### 준비

- 측정 전용 S3 프리픽스 하나 (`bench/` 등). 운영 데이터와 섞지 말 것.
- 테스트 파일: 10MB / 100MB / 500MB 영상 각 1개.
  ```bash
  # 더미 파일 생성 (내용은 무의미하지만 전송량은 동일하다)
  head -c 100M /dev/urandom > bench-100mb.bin
  ```
- 측정은 **같은 네트워크에서 3회씩** 하고 중앙값을 쓴다. 회선 상태가 흔들리므로 1회는 의미 없다.

### 재는 것

| 경로 | 어떻게 |
|---|---|
| A. 서버 중계 | `git checkout 0f92987~1` 로 옛 코드를 띄우고 `POST /api/user/post/{id}` 에 multipart 업로드 |
| B. Pre-signed 단일 | `POST /api/user/s3/presigned-url/post` 로 URL 발급 후 받은 URL 에 `PUT` |
| C. Pre-signed + Multipart 병렬 | 발급받은 파트 URL 들에 병렬 `PUT` 후 `POST /api/user/s3/multipart/complete` |

각 경로에서 **버튼 클릭부터 업로드 완료 응답까지의 시간**을 잰다.
브라우저 개발자도구 Network 탭의 총 소요 시간을 쓰거나, `curl -w "%{time_total}"` 로 재면 된다.

B 와 C 의 차이가 멀티파트 병렬의 몫이다. A 와 B 의 차이는 4절에서 봤듯 크지 않을 것이다.

### 함께 기록할 것

- 회선 상행 대역폭, EC2 인스턴스 타입과 리전, S3 리전
- 청크 크기와 병렬 수 (C에서 왜 그 값으로 정했는지 근거가 된다)
- 실패 시 재전송량. A는 처음부터, C는 실패한 청크만
- 업로드 중 백엔드 CPU, 메모리 (A에서만 올라간다)

## 7. 포트폴리오에 쓸 때

2절, 3절, 5절 숫자는 **그대로 써도 된다.** 재현 방법이 전부 문서에 있다.

업로드 지연을 설명하는 줄은 이렇게 쓴다.

> 파일을 다 받은 뒤 서버가 S3로 다시 보내는 구간이 사용자 전송이 끝난 다음에 따로 흘렀다.
> 그 구간이 통째로 없어졌다. 남은 구간은 파트로 나눠 병렬로 보내 1GB 기준 16.2초에서
> 6.5초가 됐고, 99% 에서 끊겼을 때 다시 보내는 양이 1,000MB 에서 10MB 가 됐다.

곁들일 수 있는 가장 센 한 줄은 3절이다.

> 동시 업로드 16건이 걸린 동안 조회 API 응답 시간이 7.9초였다. Pre-signed URL로 바꾼 뒤에는
> 3.1ms 로, 업로드가 없을 때(4.4ms)와 같아졌다.

5절의 **시간** 수치를 쓸 때는 측정 조건을 반드시 같이 적는다. 지연 30ms 라는 전제가 빠지면
숫자가 과장이 된다. 지연 0에서는 이득이 없다는 것도 같이 말할 수 있으면 더 좋다.
5절의 **재전송량**은 바이트라서 그런 전제가 필요 없다. 그대로 쓸 수 있다.

6절을 아직 안 쟀다면 실제 AWS 절대값은 말하지 않는다.
