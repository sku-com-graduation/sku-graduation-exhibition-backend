# 업로드 구조 개선 — 무엇을 얼마나 쟀나

전시 작품의 이미지·영상 업로드를 **서버 중계**에서 **Pre-signed URL + S3 Multipart**로 바꿨다.
이 문서는 그 개선을 숫자로 확인한 기록이다.

## 1. 두 구조의 차이

**이전 — 서버 중계** (git `0f92987` 이전, `S3Uploader.uploadToS3`)

```
프론트 ──파일 전체──▶ 백엔드 ──파일 전체──▶ S3
```

백엔드가 `MultipartFile`로 파일을 받는다는 건 **서블릿 컨테이너가 파일을 끝까지 다 받아
디스크에 떨궈 둔 뒤에야 컨트롤러가 호출된다**는 뜻이다. 그래서 두 구간이 겹치지 않고
차례로 흐른다 — 업로드 완료 시간 ≈ (프론트→백엔드) + (백엔드→S3).

**현재 — Pre-signed URL**

```
프론트 ──URL 요청──▶ 백엔드 (URL만 발급, 파일은 지나가지 않음)
프론트 ──파일 전체──▶ S3
```

영상은 여기에 S3 Multipart Upload를 얹어 청크로 나눠 병렬 전송하고, 실패한 청크만 다시 보낸다.

## 2. 이미 측정한 것 — 백엔드가 지는 부담

`ExhibitionListQueryCountTest` 옆의 [`UploadPathCostTest`](../../src/test/java/com/ghostHoliday/graduationExhibitions/performance/UploadPathCostTest.java)가
두 구조를 나란히 돌려 잰다. 예전 코드는 테스트 안에 그대로 재현해 뒀다.

```bash
./gradlew test --tests "*UploadPathCostTest"
```

**100MB 파일 1건 기준**

| 항목 | 서버 중계(이전) | Pre-signed(현재) |
|---|---|---|
| 백엔드를 통과한 바이트 | 200 MB | 48 B |
| 백엔드 임시 파일 최대 | 100 MB | 0 |
| 요청 스레드 점유 시간 | 1,017 ms | 3 ms |
| S3에 도착한 바이트 | 100 MB | 100 MB |

10MB 기준으로는 20MB / 10MB / 330ms → 48B / 0 / 2ms.

세 항목 모두 **네트워크 속도와 무관하게 구조에서 나오는 값**이라 로컬에서도 그대로 관측된다.
특히 요청 스레드 점유 시간 1초는 루프백 + 로컬 디스크에서 나온 **하한**이다. 실제 인터넷
업로드라면 그 시간만큼 톰캣 스레드가 계속 묶여 있고, 동시 업로드 N건이면 스레드 N개가 묶인다.

## 3. 아직 안 잰 것 — 사용자 체감 업로드 시간

위 표에는 "사용자가 업로드 버튼을 누르고 몇 초 기다렸나"가 없다. 그건 실제 네트워크와
S3가 있어야 의미가 있어서 로컬에서는 재지 않았다. 재려면 아래대로 하면 된다.

### 준비

- 측정 전용 S3 프리픽스 하나 (`bench/` 등). 운영 데이터와 섞지 말 것.
- 테스트 파일: 10MB / 100MB / 500MB 영상 각 1개.
  ```bash
  # 더미 파일 생성 (내용은 무의미하지만 전송량은 동일하다)
  head -c 100M /dev/urandom > bench-100mb.bin
  ```
- 측정은 **같은 네트워크에서 3회씩** 하고 중앙값을 쓴다. 회선 상태가 흔들리므로 1회는 의미 없다.

### 재는 것

| 경로 | 어떻게 |
|---|---|
| A. 서버 중계 | `git checkout 0f92987~1` 로 옛 코드를 띄우고 `POST /api/user/post/{id}` 에 multipart 업로드 |
| B. Pre-signed 단일 | `POST /api/user/s3/presigned-url/post` 로 URL 발급 → 받은 URL 에 `PUT` |
| C. Pre-signed + Multipart 병렬 | 발급받은 파트 URL 들에 병렬 `PUT` → `POST /api/user/s3/multipart/complete` |

각 경로에서 **버튼 클릭부터 업로드 완료 응답까지의 시간**을 잰다.
브라우저 개발자도구 Network 탭의 총 소요 시간을 쓰거나, `curl -w "%{time_total}"` 로 재면 된다.

### 함께 기록할 것

- 청크 크기와 병렬 수 (C에서 왜 그 값으로 정했는지 근거가 된다)
- 실패 시 재전송량 — A는 처음부터, C는 실패한 청크만
- 업로드 중 백엔드 CPU·메모리 (A에서만 올라간다)

## 4. 포트폴리오에 쓸 때

2절 숫자는 **그대로 써도 된다.** 구조적 비용이고 재현 가능하다.

3절을 아직 안 쟀다면 "업로드가 N배 빨라졌다"는 문장은 쓰지 않는다. 대신 2절로 쓴다 —
*"500MB 영상 1건을 올릴 때 백엔드를 지나가던 1GB(수신 500MB + 송신 500MB)를 0으로 만들었고,
그동안 묶여 있던 요청 스레드도 함께 풀었다."*

숫자가 없는 주장보다 재현 가능한 구조적 숫자가 낫다.
