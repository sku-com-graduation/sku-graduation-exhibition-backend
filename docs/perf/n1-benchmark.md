# N+1 개선 - 쿼리 수와 응답 시간

목록 화면들이 지연 로딩 때문에 행 수만큼 쿼리를 더 내던 것을 조인으로 한 번에 읽도록 바꿨다.
이 문서는 그 개선을 쿼리 수와 응답 시간 두 가지로 확인한 기록이다.

## 1. 무엇을 어디서 재나

| 지표 | 테스트 | DB | 왜 |
|---|---|---|---|
| 쿼리 수 | `ExhibitionListQueryCountTest`, `ListApiQueryCountTest` | H2 인메모리 | 어디서 재든 같은 값이라 빠른 쪽에서 잰다 |
| 응답 시간 | `N1LatencyBenchmarkTest` | MySQL 8.0 (도커) | H2 는 라운드트립이 없어 개선 폭이 실제보다 작게 나온다 |

쿼리 수는 Hibernate 통계의 prepared statement 수다. 실제로 DB 에 나간 SQL 개수를 센다.

## 2. 응답 시간 측정 방법

```bash
export BENCH_MYSQL_PASSWORD=아무거나
docker run -d --name sku-bench-mysql \
  -e MYSQL_ROOT_PASSWORD="$BENCH_MYSQL_PASSWORD" -e MYSQL_DATABASE=sku_bench \
  -p 3308:3306 mysql:8.0

./gradlew test --tests "*N1LatencyBenchmarkTest" -Dspring.profiles.active=mysql
```

시나리오마다 개선 전과 개선 후를 번갈아 돌린다. 워밍업 3회로 InnoDB 버퍼 풀과 JIT 를 데운 뒤
10회를 재고 p50 과 p95 를 남긴다. 회차마다 영속성 컨텍스트를 비워 1차 캐시가 섞이지 않게 하고,
두 경로가 같은 값을 돌려주는지도 매번 확인한다. 빨라졌지만 결과가 다르면 의미가 없다.

`mysql` 프로파일 없이 돌리면 테스트가 스스로 건너뛴다. H2 로 떨어진 시간을 실측으로 착각하지
않기 위해서다.

## 3. 결과

MySQL 8.0.46, 도커 컨테이너, 로컬 루프백 기준.

| 화면 | 쿼리 (전 → 후) | p50 (전 → 후) | p95 (전 → 후) |
|---|---|---|---|
| 전시 목록, 팀 200개 | 201 → 1 | 44.43ms → 1.36ms | 55.95ms → 1.59ms |
| 전시 목록, 팀 40개 | 41 → 1 | 14.31ms → 1.36ms | 22.98ms → 2.16ms |
| 팀 관리 목록, 팀 200개 | 201 → 1 | 41.74ms → 2.08ms | 44.03ms → 2.51ms |
| 계정 목록, 계정 30개 | 31 → 1 | 7.57ms → 0.93ms | 8.78ms → 1.07ms |
| 작품 상세, 팀원 8명 | 9 → 1 | 2.75ms → 0.53ms | 2.93ms → 0.98ms |

팀 200개 기준으로 쿼리는 201배, 응답 시간은 33배 줄었다.

## 4. 이 숫자를 읽을 때 주의할 것

응답 시간은 **환경에 따라 달라진다.** 위 값은 애플리케이션과 MySQL 이 같은 머신에 있는
루프백 기준이다. DB 가 네트워크 건너에 있으면 쿼리 한 번의 고정 비용이 커지므로 개선 전
쪽이 더 늘어난다. 즉 위 수치는 개선 폭의 **하한**에 가깝다.

쿼리 수는 반대로 환경과 무관하다. 그래서 두 지표를 같이 적는다. 쿼리 수는 원인을 보여주고,
응답 시간은 그 원인이 얼마짜리였는지 보여준다.

## 5. 고치지 않은 것

학생 목록도 같은 모양으로 보였지만 재보니 N+1 이 아니었다. 지연 로딩 프록시는 식별자를
이미 들고 있어서 코드가 `getId()` 만 꺼내면 초기화되지 않는다. 얻는 것 없이 조인 비용만
늘기 때문에 그 경로에는 조인을 넣지 않았다. `ListApiQueryCountTest` 에 그 사실을 테스트로
남겨 뒀다.
